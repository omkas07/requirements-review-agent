# Агент статического ревью требований (ТЗ)

BCC-HUB x MNU FinTech Hackathon. Агент читает документ с требованиями (PDF или Markdown),
выделяет отдельные требования, проверяет каждое и весь набор по ISO/IEC/IEEE 29148:2018
(п. 5.2.5–5.2.7) и IEEE 830-1998 (п. 4.3), формулирует вопросы к автору ТЗ и записывает
отчёт на русском языке в файл. Каждое замечание в отчёте опирается на дословную цитату
документа — цитаты проверяет код.

## Быстрый старт

```bash
python -m venv .venv
.venv\Scripts\activate            # Windows
# source .venv/bin/activate       # macOS / Linux
pip install -r requirements.txt
copy .env.example .env            # macOS / Linux: cp .env.example .env
# впишите ключ в .env (см. ниже)
python main.py --input examples/requirements.md --output reports/report.md
```

Нужен Python 3.11+.

## Ключ LLM

1. Откройте [aistudio.google.com](https://aistudio.google.com/) и войдите Google-аккаунтом.
2. **Get API key → Create API key**. Бесплатного тарифа достаточно.
3. Вставьте ключ в файл `.env` в корне проекта: `GEMINI_API_KEY=ваш_ключ`.

`.env` не попадает в git (он в `.gitignore`); в репозитории лежит только `.env.example` без ключей.

**Модель по умолчанию:** `gemini-3.8-flash` (Google Gemini, stable, бесплатный тариф).
Запасной провайдер — OpenAI: `LLM_PROVIDER=openai`, `OPENAI_API_KEY=...`, модель по
умолчанию `gpt-6-luna`. Модель меняется переменными `GEMINI_MODEL` / `OPENAI_MODEL`.

Для OpenAI по умолчанию `OPENAI_REASONING_EFFORT=none`: модели `gpt-6-luna` и `gpt-5.6-*` принимают
`temperature=0` только без рассуждений. Так ревью воспроизводимее: в двух прогонах подряд нарезка отличалась на 1 требование
(49 и 50), у 83% общих требований совпал статус; с рассуждениями и `temperature=1` нарезка
в двух прогонах различалась сильнее — 41 и 50 требований. Полной побайтовой повторяемости
OpenAI не гарантирует.

## Запуск

```bash
python main.py --input <файл требований> --output <файл отчёта>
```

| Параметр | Что это |
| :--- | :--- |
| `--input` | документ требований: `.pdf`, `.md` или `.txt` |
| `--output` | куда записать отчёт (Markdown); папки создаются сами |
| `-v` | подробный лог (повторы запросов к LLM) |

Примеры:

```bash
python main.py --input examples/requirements.md --output reports/report.md
python main.py --input examples/requirements.pdf --output reports/report_pdf.md
python main.py --input examples/requirements_2.md --output reports/report_2.md
```

**Куда ложится отчёт:** в файл из `--output`, для примеров выше — `reports/report.md`.
Других файлов в папке отчёта не появляется. Служебный выход агентов последнего прогона
(JSON для `eval/evaluate.py`) сохраняется в `eval/last_run.json` и в git не попадает.

Один прогон — 6 запросов к LLM, обычно 1–3 минуты. На бесплатном тарифе Gemini при
ответе 429 агент сам ждёт и повторяет запрос.

## Как устроен агент

Workflow на LangGraph, а не автономный агент: ревью должно быть воспроизводимым (temperature = 0).

```
           ┌ Разработчик ┐
Парсер ──► ├ Тестировщик ├──► Модератор ──► Верификатор ──► Агент уточнений ──► Сборщик ──► report.md
           └ Безопасник  ┘                   (без LLM)                          (без LLM)
             параллельно
```

| Узел | Что делает | LLM |
| :--- | :--- | :---: |
| Поиск «опасных слов» | словарь ISO 29148 п. 5.2.7 («быстро», «и далее», «по возможности»…) — подсказка экспертам | нет |
| Парсер | режет документ на R-01, R-02… в порядке документа, с дословной цитатой | да |
| Разработчик | хватит ли данных для кода: логика, пропущенные случаи, типы и единицы | да |
| Тестировщик | пытается написать тест к каждому требованию; критерии приёмки | да |
| Безопасник | ИБ банка: HTTP-методы, коды ответа, авторизация, персональные данные, логирование | да |
| Модератор | объединяет дубли, ставит статус 🔴/🟡/🟢, «если не исправить», проверка набора | да |
| Верификатор | выбрасывает замечания, чья цитата не найдена в документе | нет |
| Агент уточнений | вопросы к автору с вариантами и последствиями, связь с замечаниями | да |
| Сборщик | сортировка, готовность, сводка, паспорт, рендер Jinja2 | нет |

Код — гексагональная архитектура (ports & adapters): ядро (`validator/domain`, `validator/agents`)
не знает, откуда пришёл файл и какая модель отвечает.

```
main.py                    CLI
validator/domain/          модели данных, критерии, формула готовности
validator/agents/          узлы графа и сборка LangGraph
validator/prompts/         промпты (.md)
validator/ports/           интерфейсы: LLMClient, DocumentReader, ReportWriter
validator/adapters/        Gemini, OpenAI, чтение PDF/Markdown, запись отчёта
validator/templates/       шаблон отчёта report.md.j2
eval/                      эталон и оценка точности
tests/                     тесты (pytest)
```

## Отчёт

Коротко о главном (вердикт и вопросы) → 1. Паспорт прогона → 2. Сильные стороны →
3. Нарезка требований → 4. Проверка каждого требования → 5. Вопросы к автору ТЗ →
6. Проверка всего набора → 7. Сводка → 8. Итог и порядок исправления.

### Вердикт

Числовая «готовность» в отчёт не выводится: при нескольких блокирующих требованиях она
уходила в 0 и ничего не сообщала. В отчёте — вердикт и количество требований 🔴/🟡/🟢.
Внутри код (`validator/domain/scoring.py`, не LLM) считает формулу и по ней выбирает вердикт:

```
готовность = max(0, 100 − 15 × (требований 🔴) − 5 × (требований 🟡))
```

| Константа | Значение | Смысл |
| :--- | ---: | :--- |
| `WEIGHT_BLOCKING` | 15 | штраф за требование, блокирующее разработку |
| `WEIGHT_NEEDS_CLARIFICATION` | 5 | штраф за требование, требующее уточнения |
| `THRESHOLD_RED` | 50 | ниже — 🔴 |
| `THRESHOLD_GREEN` | 80 | от этого значения — 🟢 |

Вердикт:
- 🔴 **Разработку начинать нельзя** — есть 🔴 требование, блокирующий вопрос без ответа или готовность < 50;
- 🟡 **Можно начинать после исправления замечаний** — готовность < 80;
- 🟢 **Готово к разработке** — иначе.

## Оценка точности

```bash
python eval/evaluate.py                                   # последний прогон против eval/golden.json
python eval/evaluate.py --golden eval/golden_2.json        # после прогона второго ТЗ
python eval/evaluate.py --llm                             # сопоставление через LLM (1 вызов)
```

Выводит «найдено X из Y», «лишних Z» (замечания, не подтверждённые эталоном), какие
ожидаемые вопросы заданы и список пропущенного. По умолчанию сопоставление — по ключевым
словам эталона (бесплатно, повторяемо, но возможны случайные совпадения). С `--llm` модель
сопоставляет по смыслу и печатает расхождения со словами — их стоит проверить глазами.
`examples/requirements_2.md` — второе ТЗ со своим эталоном: проверка, что агент не подогнан
под один документ.

### Результаты (27.11.2026, OpenAI `gpt-6-luna`, `reasoning_effort=none`, `temperature=0`)

| Документ | Найдено пунктов эталона | Ожидаемых вопросов | Не подтверждено эталоном | Цитаты отброшены | Время | Вызовов LLM |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| `examples/requirements.md` | 23–24 из 24 (два последних прогона) | 5 из 5 | 11–16 из ~50 замечаний | 0 | ~135 с | 6 |
| `examples/requirements_2.md` | 20 из 21 (95%) | 5 из 5 | 11 из 47 замечаний | 0 | 136 с | 6 |

Цифры по первому документу совпадают при проверке по словам и через LLM; спорные пункты
просмотрены вручную. Агент от прогона к прогону немного различается (OpenAI не гарантирует
одинаковый ответ): за весь день прогонов с этими настройками — от 21 до 24 из 24. Последние два
прогона — после двух доработок: модератор не может «закрыть» требование с важными находками
экспертов (код возвращает их), а эксперты обязаны рассмотреть каждое найденное кодом «опасное слово».

Сдаваемый отчёт: `reports/report.md` (ТЗ организаторов). Метрики: `eval/last_score.json`, по второму ТЗ — `eval/last_score_2.json`; его отчёт генерируется командой выше и в репозиторий не кладётся.
