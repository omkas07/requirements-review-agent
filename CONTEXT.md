\## Задача

ИИ-агент проводит статическое ревью ТЗ финтех-проекта до разработки и пишет отчёт:

что в ТЗ неясно, противоречиво или пропущено, и что спросить у автора.



\- Задание: https://github.com/BCC-HUB/ai-requirements-validator-task

\- Сайт хакатона: https://bcchubagents.mnu.kz/

\- Тестовое ТЗ: `examples/requirements.md` («Уведомление о расходах по карте»,

&#x20; часть A — функционал, часть B — REST API). В нём специально оставлены ошибки.

\- Сдача: 27 ноября 23:59. Внутренний дедлайн — 21:00.



\## Обязательно по правилам организаторов

\- Запуск одной командой: `python main.py --input <ТЗ> --output <отчёт>`.

\- Вход: PDF обязательно, Markdown тоже.

\- Выход: отчёт на русском в файле, сгенерирован агентом. Ручной отчёт не принимают.

\- Любая LLM. По умолчанию Gemini (бесплатный ключ из aistudio.google.com), запасной — OpenAI.

\- Секреты только в `.env`; в репозитории — `.env.example`.

\- README: как получить ключ, куда положить, команда запуска, куда ложится отчёт, какая модель.

\- Каждое замечание ссылается на конкретное место ТЗ — дословная цитата, без общих фраз.

\### Правила импортов

\- `domain/` ничего не импортирует из проекта.

\- `agents/` импортирует `domain/` и `ports/`, но НЕ `adapters/`.

\### Агенты — workflow на LangGraph

Сознательно workflow, а не автономный агент: ревью должно быть воспроизводимым. temperature = 0.



```

Файл ТЗ ─► Парсер ─► ┌ Разработчик ┐

&#x20;                    ├ Тестировщик ├─► Модератор ─► Верификатор ─► Агент уточнений ─► Сборщик ─► report.md

&#x20;                    └ Безопасник  ┘                 (без LLM)                       (без LLM)

&#x20;                      параллельно

```



| Узел | Что делает | LLM |

|---|---|---|

| Парсер | Режет ТЗ на R-01, R-02… в порядке документа. Требование — любое «система должна», не только нумерованные пункты. Нарезку ТЗ не исправляет: Ф-2 с четырьмя правилами — одно требование и замечание об атомарности. Шаблонный текст (пустой чек-лист «Да / Нет») — не требование, но его незаполненность — замечание | да |

| Разработчик | Хватит ли данных, чтобы писать код: логика, пропущенные случаи, типы и единицы | да |

| Тестировщик | Пытается написать тест к каждому требованию; не получается — дефект проверяемости. Отсутствие критериев приёмки | да |

| Безопасник | ИБ в банке: персональные данные, HTTP-методы, утечки через коды ответа, авторизация, логирование | да |

| Модератор | Объединяет дубли, ставит статус, пишет `impact` | да |

| Верификатор | Цитата должна быть подстрокой документа после нормализации (регистр, пробелы, кавычки, разметка). Иначе замечание удаляется и пишется в лог | нет |

| Агент уточнений | Вопросы с вариантами там, где решает бизнес; `related\_reqs`; проставляет `question\_id` в замечания | да |

| Сборщик | Сортировка, готовность, сводка, паспорт (дата, модель, `git rev-parse --short HEAD`), рендер Jinja2 | нет |



Эксперты получают весь документ (для поиска противоречий) и список требований.

Их находки складываются в `findings: Annotated\[list, operator.add]` — параллельно, без затирания.

Все вызовы LLM — структурированный вывод по pydantic-схеме, повтор при невалидном JSON,

ретраи с паузой на 429 (у бесплатного Gemini жёсткие лимиты).



Паттерны для защиты: fan-out/fan-in (консилиум), aggregator (модератор),

guardrail (верификатор), human-in-the-loop (вопросы), workflow ради воспроизводимости.



\## Контракт данных — `validator/domain/models.py`

Меняется ТОЛЬКО через Омара. Пример данных — `eval/fake\_result.json`.



```python

class Issue(BaseModel):

&#x20;   criterion: str                  # «Непротиворечивость»

&#x20;   text: str                       # что не так

&#x20;   quote: str                      # дословная цитата для верификатора

&#x20;   impact: str | None = None       # «Если не исправить» — только blocking и важные

&#x20;   question\_id: str | None = None  # «В-1»



class Requirement(BaseModel):

&#x20;   req\_id: str                     # «R-05»

&#x20;   doc\_ref: str                    # «Ф-3», «Часть B, REST type»

&#x20;   title: str

&#x20;   quote: str

&#x20;   status: Literal\["ok", "needs\_clarification", "blocking"]

&#x20;   issues: list\[Issue] = \[]

&#x20;   suggestion: str | None = None   # «было → стало»



class Question(BaseModel):

&#x20;   q\_id: str                       # «В-1»

&#x20;   text: str

&#x20;   context: str                    # конкретная ситуация

&#x20;   options: list\[str]              # «а) январь — по дате покупки → исправить R-13»

&#x20;   related\_reqs: list\[str]         # \["R-04", "R-13"]

&#x20;   blocks: str | None = None       # что блокирует



class SetCheck(BaseModel):

&#x20;   criterion: str

&#x20;   passed: bool

&#x20;   details: str

&#x20;   refs: list\[str]

```



\## Критерии проверки

\*\*Каждое требование\*\* (ISO/IEC/IEEE 29148, п. 5.2.5): необходимость, уместность (нет лишних

деталей реализации), однозначность, полнота, атомарность, выполнимость, проверяемость,

корректность, соответствие шаблону.



\*\*Весь набор\*\* (п. 5.2.6 + IEEE 830, п. 4.3): полнота, непротиворечивость, выполнимость,

понятность, валидируемость, ранжированность, модифицируемость, трассируемость.



\*\*Финтех-чек-лист:\*\* идемпотентность, часовые пояса, валюты и единицы (тиыны/тенге),

персональные данные, семантика HTTP-методов, утечки через коды ответа, авторизация, логирование.



\*\*Опасные слова\*\* (ISO 29148, п. 5.2.7): быстро, удобно, и т.д., по возможности,

при необходимости, и далее, всегда, все… Ищутся кодом, находки передаются в промпт как подсказка.



\## Структура отчёта

1\. \*\*Коротко о главном\*\* — плашка без номера: «🔴 Готовность ТЗ: N / 100», одна фраза,

&#x20;  «Нужны ваши ответы: В-1 · В-2 · В-3» (ссылки).

2\. \*\*Паспорт прогона\*\* — документ, дата, модель, коммит, режим.

3\. \*\*Сильные стороны документа\*\* — только конкретные пункты с цитатами.

4\. \*\*Нарезка требований\*\* — таблица в ПОРЯДКЕ ДОКУМЕНТА: ID (ссылка) | где в документе | кратко | статус.

5\. \*\*Проверка каждого требования\*\* — сортировка 🔴 → 🟡 → 🟢, внутри статуса — порядок документа.

6\. \*\*Вопросы к автору ТЗ\*\* — полные вопросы с вариантами и ссылками на требования.

7\. \*\*Проверка всего набора\*\* — критерий | ✅/❌ | где.

8\. \*\*Сводка\*\* — по статусам, число вопросов, нарушения по критериям.

9\. \*\*Итог и порядок исправления\*\* — можно ли начинать разработку и тестирование, что исправить первым.



\### Блок требования

```markdown

<a id="r-05"></a>

\#### 🔴 R-05 · Ф-3 · Push при достижении порога

> «…На карту приходится максимум один такой push за календарный месяц.»



\*\*Замечания\*\*

1\. \*\*Непротиворечивость:\*\* Ф-4 требует push «независимо от истории…».

&#x20;  → \[❓ Вопрос В-2](#q-2)



&#x20;  ⚠️ \*\*Если не исправить:\*\* клиенты будут получать лишние push

&#x20;  или не получат нужный → жалобы и доработка после релиза.



2\. \*\*Полнота:\*\* не описано, что происходит после возврата…



\*\*💡 Предложение:\*\* «Не более одного push на каждое значение порога…»



\[↑ к требованиям](#nav) · \[↑ к вопросам](#questions)

```

\- Статусы: 🟢 замечаний нет · 🟡 требует уточнения · 🔴 блокирует разработку.

\- У 🟢 — одна строка: «Замечаний нет: однозначно, проверяемо…».

\- «Если не исправить» — только у 🔴 и важных 🟡.

\- Полный вопрос в блоке требования не пишется — только ссылка.



\### Блок вопроса

```markdown

<a id="q-1"></a>

\### 🔴 В-1. К какому месяцу относить покупку на стыке месяцев?

\*\*Касается:\*\* \[R-04 (Ф-2)](#r-04), \[R-13 (Критерий приёмки №2)](#r-13)



Покупка совершена 31.01 в 23:58, проведена 01.02 в 00:03.

\- а) январь — по дате покупки → исправить критерий приёмки №2

\- б) февраль — по дате проведения → исправить Ф-2



\*Блокирует: расчёт расходов и тесты на границе месяца.\*

```



\### Навигация

Только явные якоря: `<a id="r-04">`, `<a id="q-1">`, `<a id="nav">` (перед таблицей нарезки),

`<a id="questions">` (перед разделом вопросов). Автоякоря заголовков не используем —

эмодзи и кириллица их ломают. Ссылки двусторонние: таблица → требование → вопрос → требования.



\### Тон

Отчёт читает автор ТЗ — он должен хотеть исправлять, а не спорить.

\- Пишем о тексте, а не об авторе. Не «ошибка автора», «неправильно», «некорректно»;

&#x20; вместо «дефект» — «замечание».

\- Каждое замечание: что не так (с цитатой) + почему важно + как исправить.

\- Где решает бизнес — не утверждаем, а спрашиваем с вариантами.

\- Не больше 3 предложений на замечание.

\- Сильные стороны — только конкретика, без общих комплиментов.



\### Готовность — `domain/scoring.py`

Считает код, не LLM.

\- 🔴 требование −15, 🟡 требование −5, минимум 0.

\- Любое 🔴 или блокирующий вопрос → вердикт «🔴 Разработку начинать нельзя».

\- Иначе: < 50 → 🔴, < 80 → «🟡 Можно начинать после исправления замечаний», ≥ 80 → «🟢 Готово к разработке».

\- Веса и пороги — константы, описаны в README.



\## Качество

\- `eval/golden.json` — эталонный список проблем тестового ТЗ.

\- `eval/evaluate.py` — сравнивает выход агента с эталоном: «найдено X из Y, лишних Z» + список пропущенного.

\- `examples/requirements\_2.md` — второе ТЗ, чтобы проверить, что агент не подогнан под одно.

\- Тиммейт 2 после каждого прогона сообщает Омару, что пропущено, что выдумано и где резкий тон.



\## Git

\- В `main` всегда лежит запускающийся код.

\## Чего не делаем

\- Не подгоняем агента под тестовое ТЗ (никаких проверок «если есть Ф-2…»).

\- Не просим LLM писать отчёт целиком — только JSON; отчёт собирает шаблон.

\- Не правим итоговый отчёт руками — меняем промпт или шаблон и прогоняем снова.

\- Не добавляем разделы отчёта и поля в `models.py` без Омара.

\- Не усложняем архитектуру: без DI-контейнеров, БД, веб-серверов.

\- Не коммитим `.env` и ключи.

\- Интерактивный режим (`--interactive`) — только если останется время. Сдаём отчёт из обычного режима.
